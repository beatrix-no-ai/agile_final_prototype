# SBFAS — Functional Specification (for QA)

*English translation of `sbfas-fs.md` (Vietnamese original).*

**Scope:** SBFAS (School-Based FAS — school-level financial assistance) as implemented in the Admin Portal (`/admin/fas`, role: School user), including its integration with the fees module.
**Source of truth:** this document describes the *current build* — every rule below can be tested directly on the deployed app. Data is mock and not persisted (reloading the page resets all state).
**Related:** MOEFAS shares the screen rules; see the precedence rule in BR1. This document focuses on SBFAS.

## 1. Feature overview

| # | Feature | Where |
|---|---|---|
| F1 | SBFAS review queue with AI risk rating and SLA countdown | FAS → *SBFAS review queue* table |
| F2 | Decision workflow: Approve / Override / Reject with validation | Review window |
| F3 | Decision history: Granted and Declined tabs | Filter buttons above the table |
| F4 | Fee context per application: Fee payable and Account balance (top-up) | Two columns + an info block in the Review window |
| F5 | Family-level submission from the parent e-Service: creates per-child applications in the admin queue; the parent tracker and FAS card follow the decisions | Parent portal → FAS; Admin → FAS queue |
| F5 | SBFAS outcome reflected in the fee payable (subsidy on issued charges) | Fee → Student fees; charge modal |
| F6 | Recording a payment against a subsidised charge | Charge modal → *Record a payment* |

## 2. Data fields

### 2.1 SBFAS application (`SbfasApplication`)

| Field | Type | Value / format | Notes |
|---|---|---|---|
| `id` | string | `SBFASXXXX` | Reference number generated by `nextSbfasId()`: an auto-incrementing sequence padded to 4 digits, starting from the highest existing number (mocks start at `SBFAS0001`; an empty queue also starts at `SBFAS0001`). Beyond 9999 the number simply grows longer (`SBFAS10000`) — never match it with a fixed-length regex; sort by numeric value. Shown under the student's name |
| `student` | string | Full name | Must match the student record exactly |
| `studentId` | string | `S2026xxxx` | Links the application to the student's account, charges and subsidy |
| `level` | string | e.g. `P5`, `Sec 2` | Taken from the student record |
| `incomeBand` | string | `Up to S$450` / `S$451 - S$700` / `S$701 - S$1,000` / `S$1,001 - S$1,500` | Only the per-capita household income **band** is shown — the exact income never appears |
| `riskScore` | number | 0–100 | The higher the score, the harder it is for the family to pay fees |
| `recommendedTier` | enum | `Tier 1..4` | Tier 1 = highest assistance; recommended by the AI |
| `slaDays` | number | Integer | Working days **remaining** to make a decision |
| `explanation` | string | Free text | The AI's explanation, shown in the review window |
| `status` | enum | `Pending` / `Approved` / `Overridden` / `Rejected` | Can only be set through a decision |
| `sbfasTier` | enum? | `Tier 1..4` or empty | SBFAS tier granted; empty when Rejected or still Pending |
| `justification` | string? | Free text | Required for Override; stored with the decision |

### 2.2 Student record (SBFASrelated fields)

| Field | Type | Value | Notes |
|---|---|---|---|
| `sbfas` | enum | `Approved` / `Pending` / `Rejected` / `Not applied` | School-level scheme status |
| `moefas` | enum | Same values | MOE-level scheme; see precedence rule BR1 |
| `balance` | number | SGD | Education Account balance — this is **top-up money**, not FAS money |

### 2.3 Charge (fee integration)

| Field | Type | Notes |
|---|---|---|
| `fas` | enum? | `MOEFAS` / `SBFAS` / empty — the scheme **stamped when the charge is issued**; that scheme's subsidy is applied |

| `payments[]` | array | `{ id, on, amount, method: "Education account" \| "Card / PayNow" }` |

## 3. Business rules

### Decisions and history

- **BR1 — Mutually exclusive, MOEFAS first.** A student never receives both schemes at once. Effective scheme = `moefas === "Approved" ? MOEFAS : sbfas === "Approved" ? SBFAS : none`. If the data happens to have both `Approved`, **MOEFAS wins and SBFAS is ignored** (they are never added together).
- **BR2 — Approve.** Set `status = Approved`, `sbfasTier = recommendedTier`. No reason required.
- **BR3 — Override.** Requires (a) a non-blank reason and (b) a tier **different** from the AI-recommended tier — a violation blocks the action and shows an error on the relevant field. Set `status = Overridden`, `sbfasTier = the selected tier`.
- **BR4 — Reject.** Set `status = Rejected` and clear `sbfasTier`. A reason is not required.
- **BR5 — History tabs.** Granted = `Approved ∪ Overridden`. Declined = `Rejected`. Pending is in neither. The count on each tab label must match the table contents.
- **BR6 — Queue order.** Pending first, then the highest `riskScore`. Decided rows keep the risk order after the Pending block.
- **BR7 — SLA.** `slaDays ≤ 0` shows a red **Overdue** badge; `slaDays ≤ 2` highlights the remaining days in amber. Decided rows show *Closed* (the SLA no longer applies).

### AI

- **BR8 — Risk level.** `score < 35 → Low`, `35 ≤ score < 70 → Medium`, `≥ 70 → High` (badge `Low|Medium|High - score`).
- **BR9 — AI is advisory only.** The officer can always Approve as recommended, Override to a different tier (BR3), or Reject. Nothing is decided automatically.

### Fees and money

- **BR10 — Subsidy levels (based on the real MOE scheme).** MOEFAS waives **100%** of school fees and miscellaneous fees nationwide (applied uniformly across all government and government-aided schools). SBFAS is **decided by each school** (typically a 100% waiver or a 50–75% reduction) — this build uses a default of **50%**. The subsidy is applied **when a charge is generated**, per fee component; a charge keeps the subsidy recorded at issue time even if the status changes afterwards.
- **BR10a — Accompanying benefits package (in kind, does not touch charges).** MOE FAS also provides: free textbooks for the full list; school uniforms (2 sets + 2 PE sets; Primary also gets socks/shoes); meal subsidy of 7 meals a week (Primary) / 10 meals a week (Secondary); transport (Primary: 70% off school bus or S$21/month public transport pass; Secondary: S$21/month EZ-Link/SimplyGo); waiver of national exam fees (PSLE / GCE N-Level and O-Level). SBFAS (funded by alumni funds, charities and the PTA): fee waivers or reductions, book and uniform vouchers, meal vouchers/cards, partial subsidy of a personal learning device for secondary students, and funding for CCAs, camps and learning trips. These items are shown on the student's Fees page and in the Review window; they are **not** deducted from charges.
- **BR10b — Review order and reimbursement.** eFAS assesses **MOE FAS first**; families that miss the income threshold are routed to the school's SBFAS queue (consistent with BR1). If the parent is approved **after** having bought books/uniforms at the start of the year themselves: keep the invoices/receipts and apply for **reimbursement** at the school office.
- **BR11 — Subsidy ≠ top-up.** An FAS subsidy **reduces the fees** the family has to pay. A MOE top-up **adds to the Education Account balance**. The two are calculated, stored and displayed separately: the *Fee payable* column = the total still owed on unpaid charges; the *Account balance* column = the student's top-up balance. Neither changes the other.

- **BR12 — Citizenship and scheme eligibility (R4).** **MOE FAS** is for **Singapore Citizens only** (dual-citizen students `Dual (Singapore + …)` still count as citizens, since children may hold dual citizenship). **SBFAS** grants to Singapore Citizens and **Singapore PRs**; **foreign-national students are not granted SBFAS** (neither scheme applies) and **cannot apply** — the SBFAS queue never contains a foreign-national application. In the review window: PR nationality shows a yellow "SBFAS-only" warning; a foreign nationality shows a red "not eligible for either scheme — reject" warning. Warnings are advisory — the decision stays with the school user.
- **BR12 — Derived charge status.** `paid` when payments fully cover the payable amount (remainder `≤ S$0.005`); otherwise `overdue` when past `due`; otherwise `outstanding`. The status is not stored — recording a payment can turn the row to *paid* immediately.
- **BR13 — Payment rules.** Each recording is tied to exactly one charge; the amount must be > 0, at most 2 decimal places, and not more than the amount still owed. The source is *Education account* (conceptually deducts from the top-up balance) or *Card / PayNow* (payment gateway). Partial payments are allowed; each recording gets a reference `CH-xxxx-Pn`.

- **BR14 — Family-level application flow (R4-parent).** The parent submits **one application for the whole family** on the e-Service Portal (once per session). If the synced income band is the SBFAS band (not a MOEFAS band — BR10b), the system creates **one application per child** in the admin queue: ids continue the `SBFASXXXX` sequence, `studentId` points at the child's admin record, status `Pending`, and the income/household bands and sync date come from the family's sync. A MOEFAS band creates no school application (granted at MOE level); a higher band is not eligible. Decisions flow back: the parent tracker (Review = Done once every child is decided; Disbursement = In progress once anyone is granted) and the Overview FAS card (Under review → Approved when **at least one child** is granted, Not approved when all are declined); "Result per child" shows `SBFAS Tier X - Granted` / `SBFAS - Declined` with the reason.

- **BR15 — Each school decides its own applications.** Students belong to a school by level (P1–P6 → Riverbank Primary `S002`; Sec 1–4 → Greenfield Secondary `S001`). A school user sees and decides only their own school's students in the SBFAS queue (including family-submission applications: each child lands in their own school's queue). MOE HQ sees every school. Demo accounts: `S001` — Alicia Tan / Marcus Ong / Priya Nair; `S002` — Geraldine Rajaratnam (`Sch00l-Demo-26`); HQ — Daniel Lim.

## 4. QA smoke-test checklist

1. The queue loads 12 seeded applications; every student name links to that student's fees page.
2. Open a review → the block shows **Fee payable** (red) + **Account balance (top-ups)** + a note saying "these are two different amounts".
3. Approve a High-risk application → the **Granted** tab goes up by 1, the row badge is `Approved - Tier n`; Pending goes down by 1.
4. Override with no reason → blocked, focus jumps to the reason field. Override with the same tier as recommended → blocked. A valid Override → `Overridden - Tier n`.
5. Reject an application → the **Declined** tab goes up by 1, the badge is `Rejected`.
6. Find a student with SBFAS approved in Fee → Student fees: the FAS column shows `SBFAS − S$x`; the charge modal shows the subsidy block and the note that subsidy ≠ top-up.
7. Record a payment for that charge (try an amount above what is owed → rejected; exactly the amount owed → status becomes *paid*, reference `CH-…-P1` appears).
8. Reload the page — everything resets (in-memory mock): the queue returns to 12 Pending.

**Known issues (not bugs):** the chosen tier (Tier 1–4) does not yet change the subsidy level (flat 50% — BR10); a decision does not yet write back to the student's `sbfas` field immediately; MOEFAS auto-grant and the income-band API are separate stories.
